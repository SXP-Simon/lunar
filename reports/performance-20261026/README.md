# 导入、打开、重排与进程内存实测

这是 2026-10-26 的开发版模拟器基线，不能代表正式 ARM 真机，也不能据此给原生引擎与 WebView 排名。

## 身份与方法

- Lunar JS：`85a007495bfc10a90dea72b3da44722279bc190f`。APK SHA-256：`3fff66355689b9dd4d753bbee78452d89d2ea2ac6e19d4bcd3d569001600be2c`。
- `@umbrae-labs/rito-rn@0.3.0-lunar.1`，内核 `9c9111ca2fc57f63ce81c65d3c4f80cb513610ae`。
- API 36、`handwrite-api36`、4 GiB、1080×2400、420 dpi；x86_64 系统通过 ARM64 转译运行 APK。Metro/Hermes Inspector 连接，既有 reader perf 开关开启。测试期间没有编译、测试套件等并发任务。
- 411×914 CSS px，WenKai、18 px、行距覆盖1.65、左右边距24。
- 公开《白鲸》1,628,868字节、154条目、解包2,798,038字节；《草枕》竖排控制版17,940,208字节、30条目。来源和授权沿用证据分支 README。控制版只移除未启用的横排备用样式引用。
- 先将原始文件复制到测试应用私有目录并检查 SHA-256，正式输入完全匹配，见 `input-checks.json`。此前传输截断的试运行已剔除，不是应用故障。
- Hermes 测试脚本给**实际服务方法**加计时包装，调用实际导入、SQLite、fflate、Rito 和 Skia；没有模拟实现。源码工作区未修改。函数包装增加少量诊断开销，最终移除，结束测试应用。
- 导入从应用私有文件调用生产的 `importEpubFile`，不含文件选择器和内容提供者传输。每书首次新导入后再重导入两次，文件系统和进程逐渐变暖；不是三次冷启动。
- RSS 使用独立 ADB 采样约每秒一次，共556条。是整个进程驻留内存，不能当作 JS 堆，短于采样间隔的尖峰可能遗漏。

## 导入结果

| 样本 | 新导入 | 重导入2 | 重导入3 | ZIP相关同步调用占总时长 |
|---|---:|---:|---:|---:|
| 白鲸 | 3.206 s | 3.035 s | 3.140 s | 60.3%–63.0% |
| 草枕控制版 | 13.931 s | 13.652 s | 13.658 s | 95.3%–95.9% |

草枕第一次 `unzipSync` 9.325 s、`zipSync(level:0)` 3.865 s；后两次也约9.1–9.2 s与3.9 s。这些是同步 JS 调用的墙钟时间，不是“掉帧数”。白鲸首次对应1.248 s与0.596 s。元数据检查、读回、封面写入和资产索引也已独立记录；不能把嵌套阶段耗时再次相加。

当前导入会保留每条目解包文件，再生成 STORE EPUB。白鲸 STORE 包2,816,280字节，整个受管书目录实际分配6,844 KiB；草枕 STORE 包18,694,557字节、目录36,832 KiB。目录统计排除了测试用原始输入文件，包含 entries、STORE 包与封面等。保留资产文件服务于现有资源契约，不能只删掉提速。

导入期间观察到的采样最高 RSS：白鲸约1,077–1,106 MiB，草枕约1,128–1,183 MiB；对应开始前进程已约1,077–1,114 MiB。因此这些数字不是单本书额外分配的内存。

## 打开、跳转与重排

首次 UI 触发白鲸 `runtime.open` 7.354 s。API 结束表示运行时工件/画面准备完成，不是屏幕像素呈现的端到端延迟。

同一请求、排版与首次页，交替用 STORE 与原压缩包打开三轮：

| 输入 | 第1轮 | 第2轮 | 第3轮 |
|---|---:|---:|---:|
| STORE | 7.235 s | 7.664 s | 6.577 s |
| 原压缩包 | 8.080 s | 8.059 s | 6.615 s |

六次首次帧的完整绘制指令 SHA-256 一致，页文本相同。两组耗时范围重叠、各仅三次，且保留了应用后台分页/预备行为，不能据此证明等价，也不能证明 STORE 明显改善打开。未做原压缩包后续全部章节或资源性能验收。

白鲸目录跳转到第1、2、3章再返回第1章：0.480、0.411、0.279、0.214 s。章节中途字号18→20→22→18，三次重排：6.250、6.297、7.292 s。详见 `performance-summary.json` 与 `moby-ops-raw.json`。

另一进程先自动恢复白鲸，再手动打开草枕，记录 `runtime.open` 2.875 s；这不是全新进程的第一次阅读打开。该次 pinned font 准备约0.15 ms、Skia 内置字体注册约49.96 ms，不支持把数秒延迟直接归因于字体。后续可选细分探针调用失败，已剔除其数据，未把它当作应用缺陷。

## 内存与归因边界

有效首进程序列从导入到连续重开、跳转和重排，采样 RSS 约1,068→2,238 MiB。操作结束的 `dumpsys meminfo` 报告约2,134 MiB RSS；关闭阅读会话、退出阅读页并移除包装后约2,143 MiB，Inspector 强制回收后约2,092 MiB。原始 KiB 值在三个 meminfo 文件中。

这说明当前测试序列存在较高进程内存和保留，值得正式构建复测；但开发模块、调试器、分配器缓存和转译均可能影响数字，**不能据此宣称生产环境内存泄漏**。也不能把会话结束后 RSS 未立即归零当作泄漏证明。

当前最明确的优化对象是导入的同步全包 ZIP 路径。应先按资源契约评估按需读取、分块或原生处理，并用同一脚本证明收益和正确性。普通 RN 环境是否能直接使用第三方异步 Worker 方案需要单独验证，不能机械把 API 名从 Sync 换掉。

## 复现材料

- `final-records.json`：有效首进程服务计时，已排除传输错误试运行。
- `reader-core-events.json`：首进程原始 reader perf 事件；`reader-spans.txt` 为现有报告脚本的汇总，嵌套耗时有重叠。
- `memory-samples.jsonl`：原始约1秒RSS采样；`performance-summary.json` 记录窗口、版面和限制。
- `moby-open-comparison.json`：输入模式、指令哈希与页文本。
- `kusa-font-valid-records.json`、`kusa-reader-ready.json`：有效的草枕补测，失败探针不包含在内。
- 证据分支 `scripts/performance-*.js` 和 `performance-sample-memory.py` 为计时脚本；从 Lunar 仓库根目录通过 `scripts/metro-evaluate.mjs <expression.js> --async` 执行。安装 harness 前需要 APK、Metro 与书库模块已加载，刷新/重启会清除包装。内存脚本写入当前工作区 `.tmp/epub-validation/perf-device`，读当前应用PID，最多运行600秒。

测试输入仅公开样书，用户提供的三本书及其截图、文本和日志没有上传。
